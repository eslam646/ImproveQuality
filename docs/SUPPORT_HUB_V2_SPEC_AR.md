# مواصفات Support Hub V2 — المسودة الوظيفية والمعمارية

> الحالة: مسودة للمراجعة قبل أي تعديل جديد على الإنتاج  
> القرارات المعتمدة: الدعم الفوري = نوع تذكرة عاجلة، دخول غير المسجل = رابط خاص لكل مدخل بيانات، الاجتماعات = Microsoft Teams عبر Microsoft Graph، والبدء بالتصميم الكامل.

## 1. الهدف

نظام احترافي لإدارة دورة الطلب بين:

- مدخل البيانات لدى العميل.
- فريق الاختبار (Tester / QC).
- المطور.
- المديرين.

مع فصل واضح بين تذاكر التطوير العادية وطلبات التدخل الفوري التي تستهلك وقتًا من السبرنت، وتسجيل كل إجراء ومنع أي مستخدم من تعديل ما لا يخصه.

---

## 2. نموذج الهوية والعملاء

### العميل

العميل «جهة/شركة» ولا يلزم أن يكون له بريد إلكتروني.

حقول العميل:

- الاسم.
- حالة التفعيل.
- روابط المشروع.
- دليل المستخدم والوثائق.
- بيانات اختيارية أخرى يضيفها المدير.

### مدخل البيانات

مدخل البيانات هو الشخص الذي يصلنا منه الطلب ويجب أن يكون له:

- الاسم.
- البريد الإلكتروني.
- العميل/الجهة التابع لها.
- مديره المباشر إن وجد.
- حالة التفعيل.
- رابط خاص قابل للإلغاء وإعادة التوليد.

### الرابط الخاص

- لا يحتوي على اسم الشخص أو معرفه صراحة.
- يستخدم Token عشوائيًا طويلًا، والمخزن في قاعدة البيانات هو Hash فقط.
- يحدد هوية مدخل البيانات تلقائيًا؛ لا تظهر قائمة تسمح بانتحال شخص آخر.
- يستطيع المدير إلغاء الرابط أو توليد رابط جديد.
- يمكن إضافة تاريخ انتهاء واستخدام لمرة واحدة لاحقًا.

---

## 3. نموذج إنشاء الطلب

### الحقول الأساسية

1. العميل — قائمة إلزامية.
2. مدخل البيانات — تلقائي من الجلسة أو الرابط الخاص، وإلزامي.
3. نوع الطلب — إلزامي:
   - طلب تطوير جديد.
   - تعديل على طلب سابق.
   - مشكلة/عطل.
4. عنوان الطلب أو المشكلة — إلزامي.
5. التفاصيل والخطوات — نص طويل جدًا بدون حد صغير مصطنع.
6. المرفقات — إلزامية حسب إعدادات نوع الطلب.
7. فريق الاختبار — إلزامي.
8. الطلب السابق المرتبط — يظهر عند اختيار «تعديل على طلب سابق».
9. حقول مخصصة يتحكم بها المدير.

### المرفقات

- التخزين المقترح: Cloudflare R2 بدل تخزينها داخل قاعدة البيانات.
- رفع مباشر آمن بـSigned Upload URL حتى لا يمر الفيديو عبر Worker.
- صور، PDF، Office، ZIP، Logs وفيديو.
- الحد الافتراضي المقترح: 100MB للملف، ويكون قابلاً للتعديل حسب النوع.
- الفيديوهات الكبيرة جدًا: يفضّل رابط OneDrive/Google Drive أو رفع متعدد الأجزاء.
- فحص الامتداد والحجم، وروابط تنزيل موقعة، وسجل لمن رفع الملف ومتى.

### بعد إنشاء الطلب

مدخل البيانات:

- يشاهد تذاكره فقط.
- View-only لكل بيانات التذكرة.
- لا يغير الحالة أو الإسناد أو الحقول.
- لا يرفع مرفقات جديدة بعد الإنشاء.
- يستطيع فقط كتابة ملاحظة حرة.
- الملاحظة تُرسل بالبريد للمسؤولين عن الطلب ما عدا كاتبها، وتدخل سجل الأحداث.

## 4. أنواع التذاكر

### تذكرة عادية

تمر بدورة المراجعة والاختبار والتطوير المعتادة، ولا يوجد بها زر «اعتذار عن التدخل الفوري».

### دعم فوري

نوع تذكرة مميز `instant_support` ويظهر بلون وشارة منفصلين.

حقوله الإضافية:

- سبب التدخل الفوري.
- الخدمة/السيرفر/قاعدة البيانات المتأثرة.
- وقت طلب التدخل.
- وقت القبول لكل من التيستر والمطور.
- وقت البدء والانتهاء.
- مدة التدخل المحسوبة.
- تأثيره على السبرنت.
- نتيجة الجلسة.
- التذكرة السابقة المرتبطة إن وجدت.

#### قبول ورفض الدعم الفوري

- للتيستر قرار مستقل: قبول أو رفض بسبب إجباري.
- للمطور قرار مستقل: قبول أو رفض بسبب إجباري.
- رفض أحدهما لا يلغي قرار الآخر.
- عند الرفض يزال تكليفه فقط وتعود خانته لانتظار إعادة الإسناد.
- يُرسل بريد لمقدم الطلب والمديرين وباقي المسؤولين حسب إعداد To/CC.
- البريد يوضح: الاسم، الدور، السبب، التوقيت، العميل، عنوان الحالة وزر «عرض الطلب».
- الاعتذار/الرفض لا يظهر في التذاكر العادية.

## 5. دورة الحالات

يجب عدم استخدام حقل حالة واحد لكل الأطراف. نقترح ثلاثة مستويات:

### الحالة العامة

- جديد.
- انتظار مراجعة التيستر.
- نقص بيانات.
- انتظار المطور.
- قيد التطوير.
- Hold.
- تم التسليم إلى QC.
- جاري الاختبار.
- Reopened — عاد للمطور.
- Fixed.
- تم التسليم إلى مدخل البيانات.
- مغلق.
- مرفوض.

### حالة إسناد التيستر

- Pending.
- Accepted.
- Declined مع سبب.
- Reassigned.

### حالة إسناد المطور

- Pending.
- Accepted.
- Declined مع سبب.
- Reassigned.

### إجراءات التيستر

- قبول مراجعة الطلب.
- رفض الطلب لنقص البيانات/المرفقات مع سبب إجباري.
- طلب معلومات إضافية.
- تسليم الطلب للمطور.
- بدء الاختبار.
- فشل الاختبار وإعادة الطلب للمطور بسبب إجباري.
- اعتماد الإصلاح.
- التسليم إلى مدخل البيانات.

### إجراءات المطور

- قبول التكليف.
- رفض التكليف بسبب إجباري.
- قيد التنفيذ.
- Hold بسبب إجباري.
- خارج الاختصاص مع اقتراح شخص آخر.
- تم التسليم إلى QC.

كل انتقال حالة يخضع لـState Machine في الخادم، وليس مجرد إخفاء زر في الواجهة.

## 6. الصلاحيات

### المدير

- كل التذاكر والموظفين والإعدادات.
- تعديل مصفوفة الصلاحيات.
- رؤية سجل البريد والسجل الكامل.
- رؤية الشكاوى السرية والتقارير.

### مدخل البيانات

- تذاكره فقط.
- View-only.
- إضافة ملاحظات فقط.
- لا يغير الحالة أو الإسناد.
- لا يرفع مرفقات بعد الإنشاء.

### المطور

- تذاكره المسندة إليه فقط، بما فيها السابقة.
- فلاتر وحفظ Views.
- إجراءات المطور المسموحة فقط.
- لا يعدل تذكرة غير مسندة إليه.

### التيستر

- تذاكره الحالية والسابقة فقط.
- فلاتر حسب الحالة والفترة والمطور والعميل.
- لا يعدل تذكرة غير مسندة إليه.
- رفع المرفقات مسموح فقط على تذكرة مسندة إليه، إن فعّله المدير.

### التطبيق الأمني

- التحقق في Server Actions/API لكل إجراء.
- سياسات RLS دفاعية في Supabase.
- سجل Audit غير قابل للتعديل من الواجهة.
- لا نعتمد على إخفاء الأزرار وحده.

- رقم التذكرة والكود.
- نوع التذكرة وعاجل/عادي.
- العميل.
- مدخل البيانات.
- العنوان.
- التيستر وحالة قبوله.
- المطور وحالة قبوله.
- الحالة العامة.
- حالة التطوير.
- حالة الاختبار.
- التقدير والوقت الفعلي.
- تاريخ الإنشاء وآخر تحديث.

### View Builder

- إظهار/إخفاء الأعمدة.
- تغيير ترتيب الأعمدة.
- الفلاتر.
- الفرز.
- حفظ View باسم.
- View افتراضي للدور.
- إعادة الضبط.

الفلاتر تشمل: العميل، مدخل البيانات، التيستر، المطور، نوع الطلب، الحالة، العاجل، الفترة، المتوقف، المتأخر ونتيجة القبول.

## 8. البريد والإشعارات

قوالب مستقلة قابلة للتحكم:

- إنشاء طلب عادي.
- إنشاء دعم فوري.
- تكليف التيستر.
- قبول/رفض التيستر.
- تكليف المطور.
- قبول/رفض المطور.
- ملاحظة جديدة.
- تغيير حالة.
- نقص بيانات.
- تسليم إلى QC.
- فشل اختبار/Reopen.
- Fixed/Closed.
- التقرير الأسبوعي.
- شكوى سرية.
- إجازة/عمل من المنزل.

كل بريد يحتوي على زر **عرض الطلب** بحسب صلاحية المستلم.

### إعادة الإرسال

يبقى زر إعادة الإرسال الحالي، ويضاف زر جديد:

- نافذة اختيار شخص واحد أو أكثر.
- To وCC اختياريان.
- معاينة قبل الإرسال.
- تسجيل من أعاد الإرسال ولمن ومتى.

## 10. التقرير الأسبوعي

Job مجدول أسبوعيًا ينتج:

### تقرير شخصي لكل موظف

- عدد الطلبات المستلمة.

- قيد التنفيذ/Hold.

## 14. الاجتماعات — Microsoft Teams

يتم دمج Microsoft Teams رسميًا عبر Microsoft Graph API بدل بناء منصة فيديو من الصفر:

- زر «إنشاء اجتماع Teams» داخل التذكرة.
- تحديد الموعد والمدة والعنوان.
- دعوة مدخل البيانات والتيستر والمطور والمديرين المختارين.
- حفظ رابط الاجتماع ومعرفه داخل التذكرة.
- إرسال الدعوات بالبريد وإضافتها إلى تقويم Outlook عند تفعيل Calendar API.
- زر «الانضمام إلى الاجتماع» داخل صفحة التذكرة.
- تسجيل مَن أنشأ الاجتماع وموعده والمشاركين في Audit Log.
- الصوت والفيديو والشات ومشاركة الشاشة والتسجيل تتم داخل Teams حسب ترخيص وسياسات Microsoft 365.

المتطلبات:

- Microsoft 365 Tenant للشركة.
- تطبيق في Microsoft Entra ID.
- صلاحيات Graph المناسبة، وأهمها `OnlineMeetings.ReadWrite` و`Calendars.ReadWrite`.
- موافقة مسؤول Microsoft 365.
- حفظ Client ID وTenant ID وClient Secret في Cloudflare Secrets فقط.
- عدم تخزين أي Secret داخل GitHub أو قاعدة البيانات كنص ظاهر.

التسجيل، التفريغ النصي وسياسات غرف الانتظار تعتمد على ترخيص Microsoft 365 وسياسة المؤسسة.

## 15. Real-time

- Supabase Realtime لتحديث التذاكر والإشعارات والقوائم دون F5.
- عند تعديل شخص للتذكرة تظهر رسالة للمستخدم الآخر.
- تحديث العدادات والصفوف مع منع فقدان تعديلات المستخدم.
- إشعار تعارض إذا كان شخصان يعدلان نفس الكيان.

## 16. تغييرات قاعدة البيانات المقترحة

جداول/كيانات جديدة أو موسعة:

- `clients` — توسيع معلومات العميل وروابطه.
- `staff.client_id` — ربط مدخل البيانات بالعميل.
- `private_access_links` — الروابط الخاصة المشفرة.
- `tickets` — title, request_type, ticket_kind, priority, overall_status وحالات الأدوار وأوقات الدعم الفوري.
- `ticket_assignments` — تاريخ الإسنادات وقبول/رفض كل شخص بدل الكتابة فوق آخر قيمة.
- `ticket_notes` — ملاحظات منظمة مع الجمهور ونوع الكاتب.
- `attachments` — النوع والحجم والمالك وسياسة التنزيل.
- `saved_views` — الأعمدة والفلاتر والترتيب.
- `weekly_reports` — نتائج التقارير وحالة الإرسال.
- `complaints` و`complaint_events` — بيانات سرية.
- `client_resources` — مركز المشاريع والوثائق.
- `availability` — الإجازات والعمل من المنزل.
- `meetings` و`meeting_participants`.
- `audit_log` — سجل موحد غير قابل للتعديل من الواجهة.

يجب تنفيذ Migrations إضافية دون حذف الجداول أو البيانات الحالية.

## 17. خطة التنفيذ الآمنة

- نسخة احتياطية كاملة من Supabase.
- فرع Git باسم `v2-development`.
- بيئة Staging منفصلة عن الإنتاج.
- Migrations قابلة للرجوع.
- اختبارات صلاحيات لكل دور.

### المرحلة 1 — الأساس

- نموذج البيانات الجديد.
- دورة الحالات المنفصلة.
- الصلاحيات View-only.
- نموذج إنشاء الطلب بمواصفات Lark.
- المرفقات الكبيرة عبر R2.
- جدول وفلاتر وSaved Views.
- سجل أحداث كامل.

### المرحلة 2 — الدعم الفوري

### المرحلة 4 — المعرفة والتوافر

## 18. قواعد لا نتنازل عنها

1. لا تعديل مباشر على الإنتاج قبل Staging واختبار.
2. لا حذف أو استبدال للبيانات الحالية أثناء Migration.
3. لا صلاحية مبنية على إخفاء زر فقط.
4. لا روابط خاصة أو أسرار مخزنة كنص صريح.
5. لا ملفات كبيرة تمر عبر Worker؛ تستخدم Upload URLs مباشرة.
6. لا شكوى سرية تظهر في السجل العام.
7. كل إيميل/حالة/إسناد/رفض له Audit واضح.
8. لا يطبق دعم فوري كزر اعتذار عام على كل التذاكر.
